# SPEC — Bricksurance Data Core: Gen2 Expansion (Digital-Twin Completion)

**Repo:** `wryszka/bricksurance-data-core`
**Status:** Authority document. Commit to repo root as `specs/SPEC_DATACORE_GEN2_EXPANSION.md` before any build.
**Date:** 2026-08-27
**Purpose:** Close the structural gaps that prevent Bricksurance from being a credible end-to-end insurance digital twin: no policy lifecycle, one-sided balance sheet, no money administration between underwriting and claims, no customer, no renewal loop, no delegated authority. All new content is model-as-code (YAML → generator → DDL/docs/Genie), same pipeline as today. Nothing here is an app; this is the semantic and data layer the workbenches will consume when they consolidate into the gen2 workspace.

**Method compliance:** This spec follows `DEMO_BUILD_METHOD.md`. Every domain below states its canonical question, its grain, its ACORD/Lloyd's CDR crosswalk posture, its metrics, and its acceptance criteria. Deterministic seeds throughout. One schema per domain per existing convention. Deviations logged in `DECISIONS.md`.

**ACORD posture (read first):** Existing entities carry ACORD and Lloyd's CDR crosswalk fields. New entities MUST carry the same crosswalk attributes, populated at the *entity/concept* level (e.g. "ACORD: Policy / Transaction concept") with `crosswalk_status: mapped | candidate | none`. Do **not** fabricate specific ACORD element codes or XPaths — exact element-level mappings require the licensed ACORD reference and are populated in a later verification pass (`crosswalk_status: candidate` until then). Lloyd's CDR mappings for the bordereau domain (WP6) can be precise, because CDR v3.x field lists are public — use them.

## WP1 — Policy Lifecycle Event Spine (`policy_lifecycle` domain)

**The single most important addition in this spec.** The twin currently has no policy administration: underwriting ends at a decision, claims begin against generated policies, and nothing joins them. This WP creates the governed, append-only event stream that becomes the shared key fabric for every workbench and the substrate for the Group Control Tower's spine edges.

**Canonical question (Head of Operations):** "Show me everything that has ever happened to this policy — and prove nothing was edited."

**Design law:** Append-only. Events are never updated or deleted; corrections are new events with `reverses_event_id`. Current state is always a *view* over the stream, never a mutable table. This is the same append-only + supersession pattern as hb-renewal and referral rules — reuse the idiom.

### Entities

**`policy_event`** (grain: one row per lifecycle event)
- `event_id` (PK, deterministic ULID from seed), `policy_id` (FK → policy), `event_type` (code set below), `event_ts`, `effective_from`, `effective_to`, `sequence_no` (per policy, gap-free), `reverses_event_id` (nullable self-FK), `source_system` (code: UW_WORKBENCH | PORTAL | BROKER_MCP | BATCH | MIGRATION), `actor_type` (HUMAN | AGENT | SYSTEM), `actor_id`, `payload` (typed struct per event_type: sum insured delta, premium delta, coverage changes, reason codes), `prior_event_hash`, `event_hash` (chain — makes "prove nothing was edited" a live demo beat, not a claim)
- Crosswalk: ACORD policy transaction concepts, `crosswalk_status: candidate`

**`policy_version`** (grain: one row per policy per version — the SCD2 materialisation of the event stream)
- Generated by the compiler from events, never written directly. `policy_id`, `version_no`, `valid_from`, `valid_to`, `is_current`, full policy attributes as-at, `created_by_event_id` (FK). Existing `policy` entity becomes the *current* view over this (reconcile in WP0 — do not break existing consumers; add `vw_policy_current` and alias).

**`renewal_chain`** (grain: one row per policy linking predecessor/successor)
- `policy_id`, `predecessor_policy_id`, `chain_id` (stable across all renewals of one original risk), `renewal_number`. This is what makes "customer since 2019, 7th renewal" answerable — and what WP5 (renewal) and the customer dimension (WP4) hang off.

### Code set: `policy_event_type`
`QUOTED, BOUND, ISSUED, ENDORSED, MTA_REQUESTED, MTA_APPLIED, RENEWAL_INVITED, RENEWED, LAPSED, CANCELLED_INSURED, CANCELLED_INSURER, CANCELLED_NONPAYMENT, REINSTATED, NTU, EXPIRED` — with definitions in the data dictionary; every workbench uses these codes, no local variants.

### Relationships (the spine edges, made real)
- underwriting_decision → policy_event(BOUND): 1:1 where decision = bind
- claim.policy_id → policy_version (as-at loss date — claims now attach to the *version in force at loss*, which is how real insurers work and what the ResQ/Guidewire men expect)
- premium transactions (WP2) → policy_event (every earning stream starts from an event)

### Metrics
`policies_in_force` (as-at, from event stream), `new_business_count`, `retention_rate` (chain-based: renewed ÷ invited), `lapse_rate`, `cancellation_rate`, `mta_frequency`, `mid_term_exposure_change`.

### Synthetic generation
Extend the world generator: for the existing policy book, back-generate a coherent event history (seeded; every existing policy gets QUOTED→BOUND→ISSUED at minimum; ~30% get one endorsement; renewal chains built for multi-year policies; lapse/cancel consistent with existing status fields). **Hero requirement:** the golden-thread claim (CLM-2026-000001 £270k, reconciles to reserving) must trace to a policy with a full event history including one MTA before the loss — that MTA becomes a demo beat ("the sum insured changed 4 months before the loss; here is the event, the actor, the hash").

### Acceptance criteria
- `SELECT` reconstruction: `vw_policy_current` from events byte-matches the legacy `policy` rows for all existing policies (reconciliation notebook, count + checksum).
- Hash chain verifies end-to-end for every policy (verification function shipped as UC function `fn_verify_event_chain(policy_id)` — this is a demo artifact too).
- Sequence numbers gap-free per policy.
- Genie space answers: "how many policies lapsed at last renewal by LOB?" against the new views.
- One spine edge in the estate manifest can flip from `planned` to `live` using `policy_id`/`chain_id` keys (claims↔underwriting first).

## WP2 — Premium Accounting & Earning (`premium_finance` domain)

**Gap:** money enters the twin by assumption and leaves via claims; nothing is administered in between. IFRS 17 PAA and the loss-ratio metrics need an earned-premium source that survives drill-down.

**Canonical question (CFO / Financial Controller):** "Reconcile written to earned to the balance sheet for last quarter — and show me where every commission pound went."

### Entities
- **`premium_transaction`** (grain: one row per monetary movement) — `txn_id`, `policy_id`, `policy_event_id` (FK → WP1: every premium movement is caused by an event), `txn_type` (code: WRITTEN | ADDITIONAL | RETURN | REINSTATEMENT), `gross_amount`, `currency`, `ipt_amount` (rate from code set by territory), `commission_amount`, `commission_rate`, `broker_party_id`, `booked_date`, `inception_date`, `expiry_date`
- **`earning_schedule`** (grain: policy × month) — `policy_id`, `earning_month`, `earned_amount`, `method` (code: PRO_RATA_DAILY | RULE_24THS | CUSTOM), generated by a UC function `fn_earn_premium(policy_id)` — **the earning math is a governed UC function, not app code**, per estate law
- **`upr_snapshot`** (grain: month-end × LOB × currency) — unearned premium reserve, derived view materialised monthly
- **`receivable`** (grain: instalment) — `policy_id`, `instalment_no`, `due_date`, `amount`, `status` (DUE | PAID | OVERDUE | WRITTEN_OFF), `paid_date`. Minimal — enough that CANCELLED_NONPAYMENT events (WP1) have a cause, not a billing system.

### Metrics
`gross_written_premium` (reconcile with existing GWP metric — WP0 decides extend vs replace), `gross_earned_premium`, `net_earned_premium` (ceded link → existing reinsurance domain), `upr`, `commission_ratio`, `ipt_collected`, `premium_receivable_aged`. Loss ratio metric gets re-based on GEP with the change logged in the metric's governance record (this is itself a governance demo beat: "watch a certified metric definition change under proposal + attestation").

### Acceptance criteria
- Written − earned − UPR reconciles to zero by LOB by month (reconciliation view `vw_premium_proof`, shown in console Numbers tab).
- Every premium_transaction joins to a policy_event; orphan check = 0.
- IFRS 17 workbench PAA input can be re-pointed at `earning_schedule` (do not re-point in this WP; publish the view + a mapping note for the ifrs17 repo).
- Genie: "what was our earned premium in property in Q2 2026?"

## WP3 — Assets & ALM (`asset_alm` domain)

**Gap:** the balance sheet has one side. S2 market SCR and the IFRS 17 finance result rest on assumed numbers; LifeCast (annuities = ALM business) has no asset half.

**Canonical question (CIO / Chief Actuary):** "What is my duration gap against the annuity book, and what happens to own funds if rates move 100bps?"

### Entities
- **`instrument`** — `instrument_id`, `instrument_type` (code: GOVT_BOND | CORP_BOND | EQUITY | CASH | PROPERTY_FUND), `issuer`, `rating` (code set: AAA…), `coupon`, `maturity_date`, `currency`, `ma_eligible` (bool — matching adjustment)
- **`position`** (grain: portfolio × instrument × as-of month) — `portfolio_id` (code: GENERAL | ANNUITY_MA | SURPLUS), `nominal`, `market_value`, `book_value`, `clean_dirty_flag`
- **`asset_cashflow`** (grain: instrument × future month) — projected coupons/redemptions; the input to duration and MA calcs
- **`valuation_run`** — as-of date, curve set used (link to existing EIOPA curves already in solvency2 workbench — reuse, don't duplicate), run hash

### Deterministic engines (UC functions, not app code)
`fn_duration(portfolio_id, as_of)` (modified duration from cashflows + curve), `fn_duration_gap(portfolio_id, liability_ref)`, `fn_stress_mv(portfolio_id, shock_bps)`. Keep it standard-formula grade — this is a *stylised but real* asset book, labelled as such. Non-goal: full ESG stochastic asset model. QuantLib is already pinned in the LifeCast ML environment — reuse that environment key for any notebook that needs curve math.

### Volumes & seeding
~200 instruments, 3 portfolios, 36 months of history, seeded. The ANNUITY_MA portfolio must be constructed to *approximately* cashflow-match the LifeCast annuity liability profile — close enough that the duration-gap demo is honest, imperfect enough that the gap is nonzero and interesting (~0.8y gap; the demo beat is the gap, not perfection).

### Metrics
`asset_market_value`, `book_yield`, `portfolio_duration`, `duration_gap`, `ma_portfolio_spread`, `rating_distribution`.

### Acceptance criteria
- S2 workbench market-SCR inputs (interest, spread, equity) can be sourced from `fn_stress_mv` outputs — publish `vw_s2_market_inputs`; migration of the S2 workbench itself is out of scope here.
- LifeCast gains a consumable `vw_alm_annuity_match` (asset CFs vs liability CFs by bucket).
- Duration recomputes correctly under the 100bps stress (unit-test notebook with hand-checked expected values in the repo — the practitioner drill-down artifact).

## WP4 — Customer & Conduct (`customer` domain)

**Gap:** policies but no policyholders. No tenure, churn, complaints, or Consumer Duty artefacts — and Consumer Duty is board-level in the UK market.

**Canonical question (Chief Customer Officer / CRO):** "Show me fair value by product — price paid vs benefit delivered — and which customer cohorts are flagged."

### Entities
- **`customer`** — thin dimension over existing `party`: `customer_id`, `party_id` (FK), `first_policy_date`, `tenure_years` (derived from WP1 renewal chains), `segment` (code), `vulnerable_flag` + `vulnerability_basis` (reuse claims workbench's vulnerability taxonomy — one taxonomy estate-wide, reconcile in WP0), `marketing_consent`
- **`complaint`** — `complaint_id`, `customer_id`, `policy_id`, `received_date`, `category` (code set aligned to FCA DISP root causes at concept level), `status`, `outcome` (UPHELD | NOT_UPHELD | PARTIAL), `redress_amount`, `fos_referred` (bool)
- **`fair_value_assessment`** (grain: product × assessment period) — `product_code`, `period`, `avg_premium`, `avg_claims_paid`, `claims_acceptance_rate`, `avg_settlement_days`, `complaint_ratio`, `fair_value_ratio` (governed UC function), `assessment_outcome` (code: FAIR | MONITOR | ACTION), `attested_by`, `attested_at` — **this entity is the Consumer Duty demo artifact**: a governed, attested, versioned fair-value record

### Metrics
`retention_rate` (from WP1 — same metric, customer-sliced), `complaint_ratio_per_1000`, `fos_uphold_rate`, `fair_value_ratio`, `clv_simple` (labelled illustrative: tenure × avg margin — do not build a real CLV model; label it and roadmap it).

### Acceptance criteria
- Fair value ratios computed live from premium (WP2) + claims (existing) — no hardcoded numbers.
- One product seeded to land in MONITOR state (the demo needs an amber, not a sea of green).
- Vulnerability taxonomy identical to claims workbench's (single code set, both consume).
- PII posture: customer entities tagged and masked from day one (`ethnicity`-type proxies **must not exist in this domain at all** — pricing gen1's C6 lesson is codified here as a design rule, not a fix).

## WP5 — Renewal & Retention Loop (`renewal` domain, thin)

**Gap:** the twin writes business once and never manages it in force; gen2 pricing deferred renewal optimisation. This WP builds the *data* for that loop so the pricing workstream can light it later — and so `advance_period` has something to advance.

### Entities
- **`renewal_case`** (grain: one row per policy per renewal cycle) — `case_id`, `policy_id`, `chain_id` (WP1), `invited_date`, `expiry_date`, `prior_premium`, `renewal_premium_offered`, `price_walk_pct`, `competitor_ref_premium` (synthetic market quote — labelled), `outcome` (code: RENEWED | LAPSED_PRICE | LAPSED_OTHER | PENDING), `outcome_date`
- **`retention_response_curve`** (grain: segment × price-walk band) — observed renewal probability by walk band; **generated by the same calibrated logit machinery gen2 built for new-business elasticity** (reuse, cite the gen2 repo module — do not re-derive)

### Metrics
`retention_rate_by_walk_band`, `avg_price_walk`, `lapse_at_renewal_value` (GWP lost).

### The advance_period hook (estate-critical)
This domain must ship `job_advance_period`: rolls the anchor date one period, generates the next cycle's renewal invitations from in-force policies (WP1), applies outcome draws from the retention curve given whatever renewal prices are present, and appends the resulting `policy_event`s (RENEWED / LAPSED). **This is the estate's first closed loop** — decisions (renewal prices) change next period's synthetic behaviour. Deterministic given seed + decisions. Expose as a job + a callable UC-side entry point so any workbench app can put a button on it.

### Acceptance criteria
- Running `advance_period` twice from reset produces byte-identical state (determinism holds under the loop).
- Retention curve slopes correctly (higher walk → lower retention, per segment).
- After advance, `policies_in_force`, `retention_rate`, GWP metrics all move coherently and the movement is explainable on screen.

## WP6 — Delegated Authority & Bordereaux (`delegated_authority` domain)

**Gap + opportunity:** highest-ROI missing asset — genuine market pain, incumbent = spreadsheets, pure governed-data-plumbing (our game), London Market fit, Howden adjacency. Lloyd's CDR crosswalk can be **precise** here (public standard) — this becomes the estate's best ACORD/CDR showcase.

**Canonical question (Head of Delegated Authority / DUM):** "Which coverholders are outside their authority right now, and how stale is my view of their book?"

### Entities
- **`coverholder`** — `coverholder_id`, `party_id` (FK), `domicile`, `approval_status`, `audit_last_date`
- **`binding_authority`** (the binder) — `binder_id`, `coverholder_id`, `umr` (unique market reference — synthetic but format-correct), `inception`, `expiry`, `lob_scope` (array of LOB codes), `territory_scope`, `max_line_size`, `aggregate_limit`, `premium_estimate`, `commission_pct`, `claims_authority_limit`
- **`bordereau_submission`** (grain: one file received) — `submission_id`, `binder_id`, `period_month`, `bx_type` (RISK | PREMIUM | CLAIMS), `received_date`, `due_date`, `status` (RECEIVED | MAPPED | QUARANTINED | ACCEPTED), `row_count`, `dq_score`
- **`bordereau_risk_row`** / **`bordereau_premium_row`** / **`bordereau_claim_row`** — canonical row shapes **mapped attribute-by-attribute to Lloyd's CDR v3.x field names** in the crosswalk (this is the precise-mapping showcase); risk rows generate `policy_event`s of `source_system=BORDEREAU` into WP1 (delegated business enters the same spine — one twin, no side door)
- **`authority_breach`** (derived, governed) — `binder_id`, `breach_type` (LINE_SIZE | TERRITORY | LOB | AGGREGATE), `detected_by` (UC function), `bordereau_row_ref`, `status` (OPEN | WAIVED | REMEDIATED), `waived_by` — detection is deterministic UC functions; AI narrates; the waiver is maker/checker

### Data-exchange tie-in
The console's Exchange tab already does inbound mapping with (stubbed) LLM assist. WP6 gives it real payload: seed 6 coverholders × 12 months of bordereaux with realistic dirt (2 late, 1 with column drift mid-year, 1 with a line-size breach, seeded). Wire the LLM-assist mapping for real here (it's currently stubbed "high confidence" — that's a §3.5 violation once this domain lands; un-stub it in this WP or label it loudly).

### Metrics
`bordereaux_outstanding`, `avg_submission_lag_days`, `binder_utilisation_pct` (premium vs estimate), `open_breach_count`, `dq_score_by_coverholder`.

### Acceptance criteria
- CDR crosswalk table generated into docs with per-field mapping for the three bordereau row types.
- One breach detectable live by function, narrated by agent, waived under maker/checker with audit row.
- Risk bordereau rows visible in the policy event spine with correct `source_system`.
- Console Network tab shows coverholders as parties with flows.

## WP7 — Semantic layer, Genie & golden-thread updates

1. **Metric views:** every metric above becomes a governed Metric View, registered in `semantics/`, with owner + certification level (start uncertified — the console's honest-numbers pattern; certification is a demo journey, not a default).
2. **Genie contexts:** regenerate per-domain Genie instruction files; add three new spaces or extend existing by domain grouping (WP0 decides; bias toward fewer, wider spaces — cross-domain questions are the point).
3. **Golden thread v2:** extend the console's predefined flow to the full twin: *quote → bind → endorse (MTA) → earn → loss → claim → recovery → cede → reserve → SCR/CSM → fair value*. Every hop is a real key join. This is the "digital twin, end to end" demo path and the direct answer to the tower's spine problem — the thread IS the spine, demonstrated at data-core level first, workbench level second.
4. **Console tabs:** extend Model tab domains; add `Lifecycle` and `Delegated` views only if cheap — otherwise fold into existing tabs. The console is a browser, not another workbench; resist app sprawl.
